# 红线

> 红线不是「最好做到」，而是**做不到就不发布**。
> 违反任一条，先停止发布，再修复；不要用文案绕过。

## 1. 不伪造执行

- 面板不得声称已经生成 PPTX、已经跑完 ARS、已经调用上游脚本。
- 上游缺失时，只能说明缺什么、怎么准备；不能输出「已完成」。
- Host 工具不得返回伪造的文件内容、日志或退出码。
- 测试/截图/演示不得用示意图冒充真实运行结果。

**为什么**：用户会基于「已完成」做后续决策；伪造执行比失败更危险。

**执行**：`buildPrompt` 的 `noRepo` 分支；Host 缺失路径测试；人工验收。

## 2. 不伪造数据、引用与结果

- 不得编造实验数据、样本量、显著性、DOI、作者、标题、期刊。
- 缺失事实必须标注假设或待补，不得用看似合理的数字填空。
- 不得把「引用存在」说成「引用支持该论断」；不得把「格式检查」说成「学术质量保证」。
- 不得声称复现了实验、验证了数据真实性或证明了结论。

**为什么**：这是学术工具的最低诚信底线。

**执行**：PPT/ARS prompt 红线断言；ARS 完整性边界文案；人工审稿。

## 3. 不跳过人工决策点

- ARS 的研究问题、方法选择、数据解释、最终结论必须由人确认。
- 阶段 2.5 / 4.5 的完整性闸门不得被默认跳过、静默合并或自动放行。
- 「快速模式」只能减少交互，不能删除闸门；若上游模式本身允许跳过，必须明确提示。
- 面板不得自动发送 prompt；必须由人审阅后发送。

**为什么**：工具可以加速流程，但不能替人承担研究责任。

**执行**：prompt 的 checkpoint/gate 文案；`startSession` 不自动发送；验收清单。

## 4. 不越过许可证边界

- 根仓库与 PPT 包：MIT。
- ARS 包：CC BY-NC 4.0；**不得用于商业目的**，除非获得上游权利人单独许可。
- 不得移除、隐藏或改写上游版权、许可证、来源说明。
- 不得把 ARS 包整体标为 MIT，或用根 LICENSE 覆盖包级许可。
- 不得暗示本项目是上游官方项目或获得上游背书。

**为什么**：许可不是装饰；错误标注会给使用者和上游同时带来风险。

**执行**：包级 LICENSE；`ATTRIBUTION.md`；`NOTICE`；契约测试。

## 5. 不窃取数据

- 不得加入未披露的 `fetch`、XHR、WebSocket、遥测、远程日志、埋点。
- 不得把用户素材、路径、表单内容发送到本项目控制的服务器。
- 若未来加入任何网络能力，必须默认关闭、明确告知、获得同意，并更新隐私文档。
- 不得在用户不知情时读取候选 `SKILL.md` 之外的文件。

**为什么**：本地工具的首要信任来源是「它不偷看、不偷传」。

**执行**：客户端 API 扫描；Host 只读候选路径；人工代码审查。

## 6. 不引入危险执行面

- 客户端不得使用 `eval`、`new Function`、`innerHTML`、`dangerouslySetInnerHTML`。
- Host 不得 `exec`/`spawn` 上游脚本、shell 命令或包管理器。
- 不得动态加载远程代码或第三方脚本。
- 不得请求超出必要的权限，不得要求关闭沙箱。

**为什么**：面板是展示与组装层，不应成为任意代码执行入口。

**执行**：契约测试的 unsafe-API 扫描；代码审查。

## 7. 不把「可读」说成「可执行」

- `listDirectory` 成功只证明路径可读；不得显示「环境就绪」「可以生成」。
- 不得把路径存在等同于 Python/依赖/模板/ARS 运行时已安装。
- 必须在文档与 UI 中区分：路径可读、上游存在、环境可执行、任务已完成。

**为什么**：错误的能力预期会导致用户在最后一刻失败。

**执行**：状态文案 `ok` 只写「路径可读」；README/架构文档说明；验收。

## 8. 不破坏主题与可访问性

- 不得在 UI 中写死颜色、绕过 `--dsw-alias-*` token。
- 不得移除焦点环、键盘可达性或 `aria-*` 语义。
- 不得只用颜色表达状态；必须有文字。
- 不得强制覆盖 DSH 全局主题或用户的明暗选择。

**为什么**：插件必须与宿主一致，而不是把宿主变成自己的品牌。

**执行**：CSS token 扫描；设计系统评审；人工键盘/主题检查。

## 9. 不制造重复注册与命名冲突

- 侧栏 id、`main` key、模块 id、技能名、工具名必须全局唯一。
- 侧栏 id 必须等于 `main` key。
- 启用/禁用/重新启用不得产生重复注册错误。
- 不得复用其他插件的 id 或抢占其 slot。

**为什么**：DSH 的 slot 是全局命名空间；冲突会让入口消失或点错面板。

**执行**：契约测试；启用/禁用回归；人工验收。

## 10. 不隐瞒限制

- README 必须写明：不生成 PPTX、不运行 ARS、无浏览器 E2E、无上游执行测试。
- 必须写明 DSH API 可能变化、路径检查的局限、ARS 的非商业许可。
- Release notes 不得把「冒烟测试通过」写成「全面验证」。
- 已知缺口必须进入文档，而不是只留在对话里。

**为什么**：诚实的能力边界比夸大的完成度更能建立长期信任。

**执行**：README/质量文档/验收记录；发布检查。

## 11. 不破坏可回滚性

- 发布必须打 tag；不得只推 `main` 不留版本点。
- 包必须可单独禁用/移除，不牵连另一个包。
- 不得在用户未同意时自动迁移/删除 `localStorage` 数据。
- 破坏性变更必须升主版本并写迁移说明。

**为什么**：用户需要能退回到已知可用的版本。

**执行**：发布流程；CHANGELOG；人工回滚演练。

## 12. 发布前检查表

- [ ] `npm test` 全绿。
- [ ] 两个包可独立安装、禁用、重新启用。
- [ ] 真实页面中两个入口、预览、填入新会话、刷新保留均正常。
- [ ] 许可证、来源、版权、非商业边界齐全且一致。
- [ ] 没有新增网络请求、危险 API、硬编码颜色。
- [ ] 文档与实际行为一致；限制已写明。
- [ ] 版本号、tag、CHANGELOG 一致。
- [ ] 没有把未验证的能力写成已验证。

任何一项为「否」，停止发布。
