# ADR-0002：不引入共享运行时依赖

- 状态：已接受
- 日期：2026-11-09
- 决策者：项目维护者
- 相关：[架构](../architecture.md)、[契约](../contracts.md)

## 背景

两个面板的展示层高度相似：表单字段、预览、复制、路径状态、按钮、卡片、响应式布局。粗略估计约 2,000 行重复代码。直觉方案是抽一个 `@dsh-research-studio/ui` 包，两个客户端 import 它。

但 DSH 客户端 bundle 的加载方式不是普通 npm 依赖：

- `client.js` 通过 `window.__ModuleLoader__.load({ id, factory })` 注册；
- 每个 bundle 独立加载，运行时注入的服务由 DSH 提供；
- 没有证据表明第三方 client bundle 之间可以稳定地 `require` 彼此的模块；
- 引入共享包会让“只装一个面板”变成“必须同时装共享包”，增加安装失败面。

## 决策

**当前不引入共享运行时依赖。** 两个 `client.js` 保持独立、零第三方运行时依赖、无构建步骤。

用以下方式控制重复的成本：

1. **契约测试**：`tests/repo.test.mjs` 检查两个包的 slot、id、locale、schema、license、token、危险 API。
2. **设计系统**：`docs/design-system.md` 统一 token、间距、组件、状态。
3. **同构结构**：两个包的目录、Host/Client 分工、测试形状一致。
4. **同步评审**：改一个包的契约/文案规则时，另一个包必须一起过测试。

## 后果

正面：

- 每个包可独立安装、独立加载，不增加隐藏依赖。
- 没有构建步骤，源码即产物，审计简单。
- 一个包加载失败不会拖累另一个。

负面：

- 展示层重复；修一个 UI bug 可能要改两处。
- 两个包的 CSS/组件会逐渐漂移，需要评审与测试兜底。
- 新增第三个面板时，复制成本线性增长。

## 备选方案

1. **共享 npm 包**：需要确认 DSH 模块加载器能解析工作区包；未验证，风险高。
2. **构建时打包共享源码**：可行，但引入构建链、产物与 sourcemap，违背“源码即交付”的简洁性。
3. **运行时全局对象**：两个 bundle 约定挂到 `window`；脆弱、易冲突、难测试。

## 重新评估条件

满足任一条时，重新考虑共享源码（不一定是共享运行时）：

- 第三个面板出现，重复超过可维护阈值。
- DSH 明确支持 client bundle 间的模块依赖。
- 引入构建链的成本低于重复维护成本。

## 约束

- 不得为了“去重”而让一个包依赖另一个包。
- 不得在 `client.js` 中 `require` 非 DSH 提供的第三方模块。
- 任何共享方案必须先通过两个包的独立安装测试。
